# Tests

## Структура

- `test-plans/` — тест-планы: сценарии функционального и нефункционального тестирования
  платформы (API, интеграция с mock-ERP, обработка ошибок инструментов и т.п.).
- `evals/` — автоматизированная оценка качества AI-компонентов: наборы эталонных обращений с
  ожидаемой классификацией/решением/эскалацией, метрики и пороги для CI.

## Принцип

Изменение поведения агента (промпт, модель, логика) не мержится без прогона `evals` и, при
необходимости, без обновления соответствующего тест-плана.

## Проверка model conditions, revisions и OData

`python -m pytest tests/unit -q` включает MOD-005 + C3100 (R-09 не выбирается),
положительное MOD-002 + C3100, сравнение узких/несравнимых условий и изменение
ARTIFACT_VERSION при смене каждой из трёх immutable revisions.

`python -m pytest tests/integration -q` проверяет старый `/v1` и новый настоящий HTTP OData
контракт над PostgreSQL. `test_sap_odata.py` проверяет связанные справочники, CSRF, ACL,
ошибки, создание, повтор, конкурентный повтор и конфликт черновиков.
`test_orchestrator.py` и `test_identification.py` используют SapODataAdapter.

`python -m pytest tests/e2e -q` проверяет живое приложение с тремя настоящими агентами,
созданием документа через OData и строгим R-06 (отсутствие нужного правила — fail).
Ожидаемые SHA берутся из `LLM_MODEL_REVISION`, `VISION_MODEL_REVISION`, `EMBED_MODEL_REVISION`;
они должны совпадать с конфигурацией работающих vLLM и API.

Окружение: `ERP_BASE_URL`, `MOCK_ERP_URL` (для старых тестов), `MOCK_ERP_TOKEN_FILE`,
`API_URL` для E2E, PostgreSQL settings и `POSTGRES_PASSWORD_FILE`.
Для интеграционного прогона используйте отдельные PLATFORM_DB и MOCK_ERP_DB с seed из
текущих справочников; API, ERP и тесты должны указывать на эти же отдельные базы.
В E2E `POSTGRES_DB` — база тестового API. Сервисы инференса и индекс документов можно
переиспользовать без изменения данных; рабочие базы демо для тестов не используются.
