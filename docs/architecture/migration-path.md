# Переход от MVP к целевому состоянию

| | |
|---|---|
| Версия | 0.1 |
| Дата | 11.09.2026 |
| Назначение | Описание пути от реализованного MVP к целевой архитектуре |
| Связанные документы | technology-decisions.md, ADR-0003, ADR-0006, ADR-0007, workspace.dsl |

## 1. Принцип

MVP и целевое состояние различаются составом и размещением компонентов, но не структурой. Ни один переход не требует переписывания ядра: все они сводятся к замене реализации за существующей границей, вынесению существующего контейнера на отдельный узел либо добавлению компонента рядом с существующим.

Это свойство обеспечено четырьмя решениями, принятыми на старте:

| Решение | Что оно делает возможным |
|---|---|
| Порты и адаптеры для учётной системы (ADR-0006) | Замена мока на продуктивную систему без изменения агентов |
| Сервис инференса как отдельный контейнер (ADR-0007) | Вынесение на отдельный узел без изменения приложения |
| Единая коллекция с двумя представлениями (ADR-0003) | Добавление графового поиска рядом, а не вместо |
| Агентом является только интерпретация неструктурированного (ADR-0002) | Добавление классов оборудования без изменения кода ядра |

Ниже каждый переход описан в одном формате: что меняется, что остаётся, какие компоненты затрагиваются, что подлежит проверке.

## 2. Подключение к продуктивной учётной системе

**Триггер.** Получение доступа к контуру с продуктивной системой.

**Что меняется.** Реализация порта: мок заменяется адаптером OData. Появляется хранилище секретов для учётных данных подключения.

**Что не меняется.** Доменная модель, агенты, инструменты, механизм правил, модель данных платформы, контекст авторизации.

**Затрагиваемые компоненты.** Один: адаптер. Соответствие полей поставщика доменной модели существует только внутри него.

**Порядок.**

1. Сверка спецификации с фактическими сервисами; фиксация расхождений.
2. Реализация преобразования полей в адаптере OData.
3. Контрактные тесты: обе реализации порта проходят один набор.
4. Перевод разграничения доступа на полномочия учётной системы: фильтрация по территориям выполняется ею, а не платформой.
5. Параллельная работа на выборке обращений: результаты мока и продуктивной системы сравниваются.

**Риск.** Спецификация не проверена на продуктивной системе; расхождения ожидаемы (реестр рисков, R-9). Локализованы в одном компоненте.

**Что проверяется.** Контрактные тесты проходят на обеих реализациях; фильтрация по полномочиям учётной системы даёт тот же результат, что и фильтрация платформы на тех же данных.

## 3. Разделение на узлы

**Триггер.** Необходимость независимого масштабирования инференса и приложения, либо более одного ускорителя, либо требование доступности, не обеспечиваемое одним узлом.

**Что меняется.** Размещение: узел приложений, слой хранилищ, узел инференса в отдельной сетевой зоне, узел наблюдаемости. Обращение к сервису инференса становится сетевым.

**Что не меняется.** Состав контейнеров, их границы, интерфейсы между ними. Оба представления развёртывания уже описаны в модели C4.

**Затрагиваемые компоненты.** Ни одного на уровне кода: меняется описание развёртывания и адрес сервиса инференса в конфигурации.

**Порядок.**

1. Вынесение сервиса инференса на отдельный узел; адрес задаётся конфигурацией.
2. Сетевая сегментация: узел инференса не имеет исходящего доступа наружу и принимает обращения только от узла приложений.
3. Вынесение хранилищ; настройка резервного копирования на уровне слоя хранилищ.
4. Уточнение бюджетов времени: сетевое обращение к инференсу добавляет задержку.

**Что проверяется.** Время подготовки рекомендации после разделения не превышает целевого; сценарии деградации воспроизводятся в новой топологии.

**Почему не требуется кластерная оркестрация на этом шаге.** Разделение на четыре узла выполняется описанием развёртывания на каждом узле. Кластерная оркестрация становится оправданной при независимом масштабировании копий, а не при разнесении по узлам.

## 4. Добавление графового поиска

**Триггер.** Появление вопросов, требующих обхода связей глубиной более двух переходов, не выразимых запросом к учётной системе. Решение по включению в MVP принимается 20.09.

**Что меняется.** Рядом с существующим поиском добавляется графовое хранилище и ветвь обхода связей. Результаты включаются в то же ранговое слияние.

**Что не меняется.** Гибридный поиск по документам, фильтрация по правам, интерфейс сервиса поиска для агентов.

**Затрагиваемые компоненты.** Сервис поиска (добавление ветви), конвейер загрузки (построение графа). Агенты не затрагиваются: интерфейс поиска прежний.

**Ограничения при добавлении.** Не более четырёх типов узлов. Запросы к графу строятся исключительно по параметризованным шаблонам: генерация языка запросов моделью не допускается, поскольку расширяет площадь атаки внедрением инструкций. Граф не дублирует мастер-данные учётной системы: содержит связи модели, отказа, кода ошибки и документа.

**Что проверяется.** Фильтр по правам применяется к графовой ветви тем же условием, что и к остальным; полнота поиска на эталонном наборе не ухудшилась.

## 5. Добавление класса оборудования

**Триггер.** Расширение области обслуживания.

**Что меняется.** Документный корпус, справочник кодов ошибок, свод правил, эталонные случаи.

**Что не меняется.** Код. Ни агенты, ни инструменты, ни модель данных, ни оркестратор.

**Затрагиваемые компоненты.** Данные, не код. Это и есть содержание критерия приёмки AC-11.

**Порядок.**

1. Загрузка документации в конвейер; фрагменты получают метку класса оборудования.
2. Дополнение справочника кодов ошибок.
3. Разметка правил по категории согласно ADR-0004.
4. Дополнение эталонного набора случаями нового класса.

**Что проверяется.** Добавление выполнено без изменений в каталогах кода; полнота поиска по прежним классам не ухудшилась.

## 6. Делегирование согласования учётной системе

**Триггер.** Подключение к продуктивной системе.

**Что меняется.** Платформа определяет необходимость и уровень согласования, но не выполняет его: создаётся объект согласования в учётной системе, платформа ожидает результата.

**Что не меняется.** Инструмент определения уровня согласования, модель данных в части записи о согласовании, узел подтверждения человеком.

**Обоснование текущего решения.** В MVP согласование выполняется внутри платформы, поскольку иначе невозможно показать, что черновик не создаётся до одобрения. Это упрощение, а не проектное решение, и фиксируется как таковое.

**Что проверяется.** Черновик не создаётся до получения согласования из учётной системы; истечение времени ожидания приводит к эскалации.

## 7. Асинхронный конвейер загрузки документов

**Триггер.** Появление регулярного потока входящих документов вместо разовой загрузки статического корпуса.

**Что меняется.** Загрузка переводится на событийную модель: появление документа порождает разбор, разбиение, построение представлений и обновление индекса.

**Что не меняется.** Поиск, агенты, основной процесс обработки обращения. Обработка обращения остаётся управляемой запросом.

**Существенная оговорка.** Событийная модель применяется исключительно к конвейеру загрузки. Перевод основного процесса на асинхронную модель не предполагается: он синхронен по природе, а брокер добавил бы очереди и разбор недоставленных сообщений без выигрыша.

## 8. Многоарендная поставка

**Триггер.** Поставка решения нескольким организациям.

**Существенное различие.** Партнёр и территория в текущей архитектуре являются областями разграничения доступа, а не арендаторами инфраструктуры. Переход к многоарендности не сводится к добавлению признака: требуются разделение индексов и журналов по арендаторам, квоты на вычислительные ресурсы, конфигурация на стороне арендатора, раздельное резервное копирование.

**Оценка.** Это наиболее затратный из описанных переходов и единственный, затрагивающий модель данных существенно. Он вынесен отдельно именно потому, что не обладает свойством остальных: структура здесь меняется.

## 9. Сводка по стоимости переходов

| Переход | Код ядра | Модель данных | Миграция данных | Трудозатраты | Стоимость |
|---|---|---|---|---|---|
| Продуктивная учётная система | Нет | Нет | Не требуется: платформа не хранит мастер-данные. Переносится только соответствие идентификаторов мока фактическим | 60–80 ч | 350–450 тыс. ₽ |
| Разделение на узлы | Нет | Нет | Перенос томов хранилищ; индексы перестраиваются из корпуса | 16–24 ч | 90–130 тыс. ₽ плюс аренда узлов |
| Графовый поиск | Нет | Дополнение | Построение графа из существующего корпуса; обратная миграция не требуется | 30–40 ч | 170–230 тыс. ₽ |
| Класс оборудования | Нет | Нет | Дозагрузка корпуса, дополнение справочников. Существующие индексы сохраняются | 8–12 ч | 45–70 тыс. ₽ |
| Согласование в учётной системе | Частично | Нет | Незавершённые согласования дорабатываются в прежнем порядке | 12–16 ч | 70–90 тыс. ₽ |
| Асинхронная загрузка | Нет | Нет | Корпус сохраняется, меняется способ пополнения | 24–32 ч | 140–190 тыс. ₽ |
| Многоарендность | Да | Да | Разделение существующих индексов, журналов и записей аудита по арендаторам. Единственный переход с необратимой миграцией | 200+ ч | от 1,2 млн ₽ |

Оценки трудозатрат рассчитаны по ставкам экономического обоснования и не включают коэффициент трения; для промышленного внедрения применяется коэффициент 2,5.

**Ключевое свойство миграции данных.** Шесть переходов из семи не требуют преобразования существующих данных, а только их дозагрузки или переноса без изменения структуры. Причина в том, что платформа хранит состояние процесса, знания и права, но не мастер-данные: при смене учётной системы мигрировать оказывается нечего. Седьмой переход, многоарендность, требует разделения существующих записей и является необратимым.

Шесть переходов из семи не затрагивают код ядра. Седьмой обозначен как структурное изменение, а не развитие.
