## 1. Контур и модель нарушителя

Все модели размещены локально (ADR-0001). Данные партнёров не покидают периметр. Обращений к внешним сервисам генеративного искусственного интеллекта в контуре продукта нет.

Рассматриваемые нарушители:

| Нарушитель | Возможности | Основной риск |
|---|---|---|
| Внешнее лицо через канал обращений | Формирует произвольный текст и изображение | Внедрение инструкций, попытка получить чужие данные |
| Представитель партнёра | Легитимный доступ к своим объектам | Получение данных других партнёров, доступ к внутренним документам |
| Сотрудник одной территории | Легитимный доступ в своей зоне | Получение данных другой территории |
| Сотрудник с расширенными полномочиями | Право обхода блокирующих правил | Обход без основания, отсутствие следа |

Внешний нарушитель с доступом к инфраструктуре в модели MVP не рассматривается: узел арендован, доступ по ключу, порты закрыты для внешних подключений.

## 2. Разграничение доступа

Два независимых измерения: территориальное и по уровню конфиденциальности документов (PRD, раздел 3.3).

**Точка контроля — источник данных.** Контекст авторизации является обязательным параметром каждого метода порта адаптера и каждого поискового запроса. Вызов без него невозможен по сигнатуре (ADR-0006).

**Фильтрация готового ответа не применяется.** Данные, недоступные пользователю, не должны попадать в контекст модели: после попадания утечка становится вопросом формулировки запроса.

**Отказ вместо пустого результата.** Обращение к объекту чужой территории возвращает отказ и фиксируется в аудите. Пустой результат неотличим от отсутствия данных и скрывает ошибку разграничения.

**Обе ветви поиска фильтруются одним условием.** Плотная и разреженная ветви применяют один фильтр по уровню конфиденциальности. Раздельная фильтрация создала бы возможность получить закрытый фрагмент через одну ветвь в обход другой (ADR-0003).

**Наименьшие полномочия агентов.** Каждому агенту доступен только перечень инструментов, необходимых для его операции. К учётной системе, в MVP — к её моку, обращается только адаптер: ни агенты, ни интерфейс пользователя прямого доступа к ней не имеют.

Проверяется критериями приёмки AC-3 и AC-4.

### 2.1 Два слоя контроля: выдача и чтение сохранённого

Фильтр в поисковом запросе ограничивает то, что попадает в контекст модели. Он не ограничивает то, что читают позже: сохранённая рекомендация, ссылки на фрагменты и снимки шагов переживают запрос и могут быть прочитаны другим пользователем — например представителем партнёра того же клиента. Это отдельный слой контроля с отдельной точкой применения.

| | Слой выдачи | Слой чтения |
|---|---|---|
| Что ограничивает | Фрагменты, попадающие в запрос к модели | Сохранённый результат разбора |
| Где применяется | Фильтр в запросе к хранилищу векторов, до ранжирования | Условие в запросе к хранилищу состояния |
| По каким правам | Автора обращения на момент разбора | Читателя на момент чтения |

Правила слоя чтения:

- **Права берутся текущие.** Территория обращения, если она определена, должна входить в территории читателя. Авторство доступа не даёт: отзыв территории закрывает обращение и тому, кто его создал.
- **Скрывается вывод целиком, а не отдельные слова.** Если хотя бы один источник гипотезы недоступен читателю, не возвращаются ни гипотеза, ни уровень обоснования, ни ссылки: ответ содержит признак ограничения и пояснение. Удаление названий из текста оставило бы содержание закрытого документа в самом изложении.
- **Ограничение выполняется в запросе.** Уровни доступа читателя передаются в запрос к хранилищу состояния; закрытый материал не извлекается и не отбрасывается после сборки ответа. Это то же правило, что для поиска.
- **Техническая трассировка доступна только служебным ролям.** `GET /v1/requests/{id}/steps` возвращает снимки шагов и вызовы инструментов, включая текст запроса к модели вместе с найденными фрагментами. Представителю партнёра он недоступен даже на собственном обращении; отказ фиксируется в аудите. Поля разбора — извлечение из текста, чтение таблички, проверка кода, кандидаты по серийному номеру — в ответе на чтение обращения выдаются только служебным ролям.

Сохранённый внутренний материал обращения сотрудника представителю партнёра в проверенных сценариях не выдаётся; проверки перечислены в критерии AC-4 и в сквозных тестах. Утверждение ограничено проверенными путями чтения — `GET /v1/requests/{id}` и `/steps`; появление новых способов чтения требует повторной проверки.

## 3. Декомпозиция контроля ввода и вывода

Контроль разделён на четыре независимых механизма. Объединение недопустимо: они срабатывают в разные моменты, на разных данных и требуют разной реакции.

### 3.1 Входной контроль текста обращения

| | |
|---|---|
| Что проверяет | Персональные данные сверх ожидаемых; попытки внедрения инструкций; запросы вне предметной области |
| На каких данных | Исходный текст до любой обработки |
| Почему отдельно | Единственный механизм, работающий до попадания текста в контекст модели |
| При срабатывании | Персональные данные помечаются для журналирования, но текст не искажается: он несёт диагностическую информацию. Внедрение инструкций — обращение отклоняется с уведомлением. Запрос вне области — вежливый отказ без обработки |

Текст обращения является недоверенным вводом независимо от роли отправителя.

До смысловых проверок отсекается технически некорректный ввод: превышение допустимой длины текста и недопустимая кодировка.

### 3.2 Входной контроль результата распознавания изображения

| | |
|---|---|
| Что проверяет | Внедрение инструкций в распознанном тексте; правдоподобие извлечённых идентификаторов |
| На каких данных | Результат работы модели обработки изображений |
| Почему отдельно от 3.1 | Данные появляются позже и порождаются моделью. Изображение с нанесённым текстом — известный способ обхода контроля, проверяющего только исходное сообщение |
| При срабатывании | Результат распознавания отбрасывается, запрашивается ручной ввод серийного номера |

### 3.3 Предохранитель безопасности

| | |
|---|---|
| Что проверяет | Признаки опасности для человека и имущества |
| На каких данных | Очищенный текст обращения, до вызова агентов |
| Почему отдельно | Единственный контроль, срабатывающий до и помимо рассуждения. Не может быть отменён правилом, агентом или оператором в обычном порядке |
| При срабатывании | Немедленное прерывание процесса и эскалация независимо от прочих результатов |

Реализован правилом, а не запросом к модели. Действует на любом этапе, включая ожидание ответов на уточняющие вопросы.

### 3.4 Выходной контроль

| | |
|---|---|
| Что проверяет | Существование упомянутых артикулов, моделей и кодов ошибок в справочниках; принадлежность значения решения классификатору; отсутствие обещаний сроков и стоимости, не подтверждённых договором; наличие ссылок на источники |
| На каких данных | Сформированная рекомендация до показа пользователю |
| Почему отдельно | Проверяет результат работы модели, а не ввод. Требует обращения к справочникам, то есть выполняется после получения фактов |
| При срабатывании | Рекомендация не показывается. Повторная генерация не более одного раза, затем эскалация |

Ответ без ссылок на источники не выдаётся ни при каких обстоятельствах.

### 3.5 Ограничение предлагаемых проверок

Отдельный механизм в составе цикла уточнения (ADR-0008): перечень допустимых действий ограничен ролью обратившегося. Представителю партнёра не предлагаются действия, требующие вскрытия корпуса, работы с нагретыми узлами или разборки.

Реализовано правилом, а не указанием в запросе к модели: ошибка здесь способна причинить вред человеку.

### 3.6 Косвенное внедрение через документный корпус

Отдельный вектор, не покрываемый механизмами 3.1 и 3.2: инструкции, внедрённые не в обращение, а в документ, попавший в корпус. При извлечении такого фрагмента поиском он оказывается в контексте модели наравне с легитимным содержанием, а входной контроль к нему не применялся.

| | |
|---|---|
| Где возникает | Загруженный документ: руководство из недостоверного источника, внутренний документ, изменённый сотрудником |
| Почему опаснее прямого внедрения | Действует на всех пользователей, извлекающих фрагмент, и сохраняется до перестроения индекса |
| Меры на этапе загрузки | Корпус формируется контролируемо; каждый документ имеет зафиксированный источник, контрольную сумму и уровень доверия; загрузка выполняется явной командой, а не автоматически по появлению файла |
| Меры на этапе применения | Извлечённый фрагмент передаётся модели как данные, а не как указания. Полномочия агента ограничены перечнем переданных правил: указание, внедрённое во фрагмент, не способно назначить маршрут вне свода правил |
| Меры на этапе вывода | Выходной контроль проверяет существование упомянутых сущностей и принадлежность значения классификатору |
| Остаточный риск | Искажение диагностической гипотезы в пределах допустимых маршрутов. Снижается обязательностью ссылок на источники: подозрительный фрагмент виден оператору |

Пользовательский ввод в корпус не попадает ни при каких обстоятельствах: это исключает наиболее вероятный путь отравления.

## 4. Соответствие OWASP Top 10 для приложений с языковыми моделями

| Риск | Мера в решении |
|---|---|
| Внедрение инструкций | Раздельный контроль текста и результата распознавания (3.1, 3.2). Модель не имеет доступа к учётной системе; полномочия агента ограничены перечнем переданных правил |
| Небезопасная обработка вывода | Выходной контроль (3.4). Значения проверяются по справочникам, свободный текст в исполняемые действия не транслируется |
| Раскрытие чувствительных данных | Фильтрация в источнике по двум измерениям. Данные вне зоны ответственности не попадают в контекст |
| Избыточные полномочия агента | Разделение рассуждения и исполнения (ADR-0002). Запись только через детерминированный исполнитель после подтверждения человеком |
| Чрезмерное доверие к выводу модели | Обязательные ссылки на источники, проверка существования сущностей, предварительность квалификации гарантии, подтверждение человеком |
| Отравление данных и модели | Корпус формируется контролируемо: публичная документация производителей и внутренние документы. Пользовательский ввод в корпус не попадает |
| Отказ в обслуживании | Бюджеты времени, ограничение повторов, размыкатель (ADR-0007) |
| Уязвимости цепочки поставок | Фиксация версий моделей, образов и лицензий; контрольные суммы весов |

Внедрение в язык запросов к хранилищу неприменимо: поисковый запрос не транслируется в исполняемый язык. Это одно из оснований отказа от графового поиска в MVP (ADR-0003).

## 5. Секреты

| Категория | Порядок хранения |
|---|---|
| Учётные данные хранилищ | Механизм секретов среды исполнения. В файл переменных окружения и в репозиторий не попадают |
| Ключ доступа к сервису инференса | Настоящий, генерируется при развёртывании и передаётся механизмом секретов среды исполнения. Сервис слушает только внутренний интерфейс, ключ — дополнительный рубеж при локальном размещении |
| Учётные данные учётной системы | В MVP отсутствуют: используется мок. Для целевой реализации — хранилище секретов, не переменные окружения |
| Ключи наблюдаемости | Механизм секретов среды исполнения |

**Файл переменных окружения не является средством хранения секретов.** Он содержит только несекретную конфигурацию: адреса служб, порты, наименования моделей, параметры поиска. Разделение принято сознательно: такой файл читается любым процессом контейнера, попадает в вывод диагностических команд и по невнимательности оказывается в репозитории.

Секреты передаются механизмом секретов среды исполнения: файлами, монтируемыми в контейнер средствами оркестрации, и переменными сборочной среды при автоматической сборке. В репозитории находится только образец несекретной конфигурации.

Секреты не передаются аргументами командной строки и не запекаются в образ контейнера.

Секреты генерируются один раз при первом развёртывании и при повторном не перевыпускаются: иначе они рассогласуются с уже созданными томами хранилищ.

Ротация в MVP не автоматизирована. Для целевой архитектуры предусмотрено хранилище секретов с ротацией и выдачей по запросу.

**При компрометации.** Немедленно: перевыпуск скомпрометированного секрета, перезапуск затронутых служб, проверка записи аудита на обращения в период компрометации. Затем: установление способа утечки, проверка истории репозитория на попадание секрета в отслеживаемые файлы, при подтверждении — перезапись истории и принудительное обновление. Учётные данные хранилищ перевыпускаются вместе с пересозданием томов, поскольку рассогласование секрета с существующим томом делает хранилище недоступным. Событие фиксируется в журнале с указанием затронутых секретов, времени обнаружения и выполненных действий.

## 6. Граница сетевого периметра

Требование локального контура обеспечивается на двух уровнях.

**Действительная граница** — правила группы безопасности на стороне площадки: разрешены только необходимые исходящие соединения, входящие ограничены доступом по ключу.

**Вспомогательный уровень** — локальная блокировка известных адресов внешних сервисов генеративных моделей. Защищает от случайного обращения из библиотеки или примера кода, но не является средством защиты от намеренного обхода и не должна так называться.

Все порты сервисов слушают внутренний интерфейс узла. Наружу не публикуется ни один сервис, кроме доступа по ключу для администрирования.

## 7. Резервное копирование

| Данные | Порядок |
|---|---|
| Состояние и аудит | Ежедневная выгрузка хранилища на отдельный том, переживающий пересоздание узла |
| Векторные представления | Восстанавливаются повторной загрузкой корпуса; резервирование не требуется |
| Веса моделей | Хранятся на отдельном томе; при утрате загружаются заново |
| Документный корпус | Хранится в репозитории |
| Конфигурация | Хранится в репозитории, кроме секретов |

Критично для сохранности только хранилище состояния: оно содержит аудиторский след, который невозможно восстановить.

## 8. Аудит

Аудиторский след ведётся в собственном хранилище (модель данных: `PROCESS_STEP`, `TOOL_CALL`, `EVIDENCE`, `AUDIT_EVENT`, `APPROVAL`).

Внешний инструмент трассировки является средством разработки и **источником доказательств не является**. Его недоступность не влияет на доказательную часть и не блокирует обработку обращений.

Фиксируются: все вызовы инструментов с параметрами и результатом; применённые и рассматривавшиеся правила; отказы в доступе; причины эскалации; факты обхода блокирующих правил с указанием основания и лица; подтверждения оператора.

Доступ к журналам и к инструменту трассировки, содержащим тексты обращений, имеет ограниченный круг ролей; обращения к журналам фиксируются.

### 8.1 Retention / срок хранения

**Current MVP.** Автоматические TTL, удаление по возрасту и архивирование записей audit store не реализованы. Решения, согласования, execution grants, шаги, вызовы инструментов и ERP action audit сохраняются до административной очистки; то же относится к raw user input и вложениям в базе платформы. Это ограничение MVP, а не утверждённая политика бессрочного хранения.

У технических средств есть отдельные ограничения: Docker JSON logs ротируются по размеру (20 МБ × 5 файлов на контейнер), Prometheus хранит метрики 15 дней. Выгрузки базы удаляются по `BACKUP_KEEP_DAYS` (по умолчанию 14 дней). Ротация логов и резервных копий **не удаляет записи из audit store** и не заменяет политику хранения бизнес-доказательств.

**Target / production policy.** Ниже предложены настраиваемые архитектурные defaults до согласования с legal/compliance и владельцем данных. Они не являются юридически обязательными сроками и ещё не реализованы в приложении.

| Категория | Состав | Предлагаемый default и начало отсчёта |
|---|---|---|
| Бизнес-доказательства и аудит действий | Решения, согласования, execution grants, версии правил и ссылки на evidence, аудит действий ERP | 3 года после закрытия обращения; связанный минимальный доказательный пакет хранится согласованно |
| Технические журналы приложения | Ошибки и эксплуатационные события без избыточного содержимого обращения | 30 дней с события |
| Метрики | Численные показатели сервисов и инфраструктуры | 90 дней с измерения |
| Debug traces / LLM traces | Диагностические трассы, промпты и ответы, если их сохранение разрешено | 14 дней с события; это телеметрия, а не источник бизнес-доказательств |
| Вложения и исходный пользовательский ввод | Фотографии, raw request text и их копии в технических снимках | 30 дней после закрытия обращения; обоснованное исключение для доказательного пакета согласует владелец данных |

Политика должна учитывать копии данных в снимках шагов, промптах, архивах и резервных копиях: короткий TTL вложения сам по себе не удаляет его копии. Для доказательств сохраняются необходимые версии правил и использованных фрагментов либо доступный архив этих версий. Изъятия на время спора или расследования оформляются отдельно; удаление выполняется согласованно с зависимостями и фиксируется в аудите. Механизм очистки, архивирования и таких исключений относится к target.

При A-1 = 300 обращений/мес получается 3 600 обращений в год, но число и размер событий на обращение, объём вложений и коэффициент сжатия не измерены. Оценка хранения в ГБ без этих данных не приводится.

## 9. Известные ограничения MVP

Перечисляются явно, поскольку умолчание о них хуже их наличия.

1. Ротация секретов не автоматизирована; выделенное хранилище секретов не применяется.
2. Шифрование данных при хранении не применяется: обеспечивается средствами площадки.
3. Единый узел является единой точкой отказа (ADR-0007).
4. Адаптер учётной системы не проверен на продуктивной системе; утверждения о совместимости являются проектными предположениями.
5. Многопользовательская изоляция на уровне арендаторов не реализована: система рассчитана на одну организацию.
6. Локальная блокировка исходящих адресов не защищает от намеренного обхода.
7. Слой чтения различает уровни конфиденциальности, но отдельной повторной проверки принадлежности партнёрского документа конкретному партнёру при чтении сохранённого материала нет. В текущем корпусе документов уровня «Партнёрский» нет вовсе, поэтому путь непроверяем; перед добавлением такого документа проверку нужно реализовать и покрыть тестом.
8. Проверка неподтверждённых утверждений гипотезы — детерминированная, по словам и их семействам. Она отсекает названные категории утверждений о гарантии, оплате, стоимости и сроках, но не является доказательством смыслового соответствия гипотезы источникам.
9. Автоматическое ограничение срока хранения audit store, исходных обращений и вложений не реализовано; записи остаются до административной очистки. Предлагаемые production defaults раздела 8.1 требуют согласования и отдельной реализации.
10. Заголовок `X-User-Id` в MVP — trusted/demo identity context, а не полноценная authentication. При прямом сетевом доступе к API вызывающий может подставить идентификатор другого известного пользователя; реестр платформы определит его права, но не докажет личность отправителя. Компенсирующая мера MVP — публикация API только на loopback и доступ через SSH tunnel. Production target — corporate SSO/OIDC либо mTLS/иной подтверждённый identity mechanism; `AuthContext` должен формироваться из аутентифицированной identity. Текущая схема не защищает от spoofing внутри доверенного сетевого контура.
