## Узел

Стенд один: на нём работают сервисы инференса, приложение, хранилища и наблюдаемость (ADR-0001). Разделение на четыре узла отнесено к целевой архитектуре (migration-path 3).

| Параметр | Ранее планировалось | Фактически, MVP GPU node |
|---|---|---|
| Ускоритель | RTX 6000 Ada, 48 ГБ | NVIDIA GeForce RTX 4090; runtime сообщает 49 140 МиБ; драйвер 580.178.04 |
| Архитектура | Ada Lovelace | Ada Lovelace, требование ADR-0005 о поддержке AWQ выполнено |

Коммерческое наименование ускорителя на расчёт не влияет: наблюдаемые ёмкость видеопамяти и поколение архитектуры совпадают с расчётными. Первый узел был утрачен (у него забрали ускоритель), поэтому развёртывание проверено дважды на разных машинах.

## Видеопамять

Экземпляры vLLM резервируют долю **полного** объёма видеопамяти, заданную параметром `--gpu-memory-utilization`. Поэтому потребление определяется настройкой, а не размером весов: свободное сверх весов уходит в кэш ключей и значений. Отдельные цифры на модель не снимаются — измеряется сумма.

| Назначение | Доля (`infra/.env`) | Резервируется | Ограничение контекста |
|---|---|---|---|
| Языковая модель, AWQ | 0,40 | ≈ 19,2 ГБ | 32 768 лексем |
| Модель обработки изображений, AWQ | 0,27 | ≈ 13,0 ГБ | 16 384 лексемы |
| Модель векторных представлений | 0,08 | ≈ 3,8 ГБ | 8 192 лексемы |

Измерено при трёх загруженных моделях и простое: **34 505 МиБ занято из 49 140 МиБ**, запас 14,6 ГБ — 30% при требуемых по допущениям 25%. Запас держится ради кэша ключей и значений при одновременных обращениях; поднимать доли до исчерпания видеопамяти нельзя.

## Измеренное время

Сквозной сценарий: обращение «HP LaserJet Pro M4103dw, серийный номер указан, ошибка 50.2», приём, разбор, подтверждение оператором, черновик в учётной системе. Три прогона, `tests/eval/measure.py`, MVP GPU node. Первый прогон прогревает компиляцию грамматики структурированного вывода и приводится отдельно.

| Измерение | Холодный, с | Медиана, с |
|---|---|---|
| Сценарий целиком | 1,88 | **1,72** |
| Разбор обращения (приём до ожидания подтверждения) | 1,83 | 1,66 |
| Подтверждение и черновик | 0,06 | 0,06 |
| Шаг `identification` | 1,02 | 0,83 |
| Шаг `knowledge` | 1,69 | 1,53 |
| Шаг `create_draft` | 0,03 | 0,03 |
| Шаг `fulfillment` | 0,03 | 0,03 |
| Вызов модели `llm.context` | 0,96 | 0,77 |
| Вызов модели `llm.knowledge` | 1,65 | 1,50 |
| Гибридный поиск `search.hybrid` | 0,03 | 0,02 |
| Любой вызов учётной системы `erp.*` | 0,01 | 0,01 |
| Правила, срочность, гарантия, контроль вывода | 0,00–0,01 | 0,00–0,01 |

Что из этого следует:

1. Время сценария определяют два вызова языковой модели: 0,77 с и 1,50 с при 1,72 с на сценарий целиком. Детерминированная часть — правила, срочность, маршрутизация, подбор исполнителя, контроль вывода — на этом масштабе не измерима.
2. Длительности шагов в сумме превышают время запроса, измеренное клиентом (2,36 с против 1,66 с). Отметки шагов проставляет хранилище состояния, общее время засекает клиент, поэтому величины сопоставимы только по порядку. Расхождение подлежит проверке при включении трассировки вызовов модели.
3. Целевое время подготовки рекомендации «до 60 секунд» выдерживается с запасом в тридцать раз. Запас расходуется при добавлении Policy Agent, уточняющего раунда и распознавания таблички: каждый добавляет один-два вызова модели того же порядка.
4. Поиск и учётная система на время отклика не влияют: 0,02 с и 0,01 с против бюджетов 5 с по ADR-0007.

Сопоставление с бюджетами ADR-0007:

| Операция | Бюджет | Медиана | Запас |
|---|---|---|---|
| Чтение из учётной системы | 5 с | 0,01 с | 500× |
| Запись в учётную систему | 15 с | 0,01 с | 1500× |
| Вызов языковой модели | 60 с | 0,77–1,50 с | 40–78× |
| Поиск | 5 с | 0,02 с | 250× |

Бюджеты сохраняются без изменений: они рассчитаны на деградацию под нагрузкой и на длинный контекст, а не на измеренный одиночный проход.

Распознавание таблички отдельно не хронометрировалось: оно проверялось в составе оценочного набора Context Agent — 24 проверки, включая чтение 17 эталонных изображений, весь набор 46 с. Бюджет зрения 30 с не приближался.

## Допущения по нагрузке

Измерения сняты на одиночном проходе. Допущения ниже остаются допущениями до нагрузочных измерений.

| Параметр | Допущение | Состояние |
|---|---|---|
| Одновременных пользователей, максимум | 3 | не проверено |
| Одновременно обрабатываемых обращений | 2–3 | не проверено |
| Обращений в месяц | 300 | не проверено |
| Вызовов языковой модели на одно обращение | 4–6 | фактически 2 при текущем составе агентов |
| Доля обращений с изображением | 20% | не проверено |
| Типовой объём входного контекста | 4 000–8 000 лексем | не измерено |
| Типовой объём ответа | 500–1 500 лексем | не измерено |
| Целевое время подготовки рекомендации | до 60 секунд | выдерживается: 1,72 с |
| Объём корпуса | 26 документов, ≈1 500 фрагментов | фактически 9 документов, 46 фрагментов |
| Запас по видеопамяти | не менее 25% | выдерживается: 30% |

Корпус меньше планового на порядок: он охватывает два класса оборудования из шести (conformance, раздел 7). На время поиска это не влияет — 46 фрагментов и 1 500 фрагментов для Qdrant неразличимы; влияет на полноту выдачи, что и отражается отказом отвечать при отсутствии подходящих фрагментов.

## Осталось измерить

1. Пропускная способность при трёх одновременных обращениях и поведение кэша ключей и значений под ними.
2. Время холодного старта стека после пересоздания узла: сейчас известно только, что загрузка трёх моделей занимает единицы минут.
3. Время распознавания таблички отдельным замером и доля обращений, где оно требуется.
4. Объём входного контекста и ответа в лексемах — нужен для оценки стоимости при переходе на внешнюю модель (migration-path).

Показатель числа запросов в секунду для данной системы малоинформативен: сценарий предполагает несколько последовательных вызовов модели на одно обращение при числе одновременных пользователей, измеряемом единицами. Основным показателем принимается время подготовки рекомендации.
