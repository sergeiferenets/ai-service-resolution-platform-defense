Записка описывает, как система разворачивается, конфигурируется, восстанавливается и наблюдается. Команды и детали реализации — в `infra/README.md`, здесь — принятые решения и их основания.

## 1. Размещение

MVP размещается на одном арендованном узле с ускорителем; все службы — контейнеры под управлением Docker Compose (ADR-0007). При одной копии каждой службы, единицах одновременных пользователей и одном ускорителе кластерная оркестрация не даёт ни масштабирования, ни доступности. Бессерверное исполнение несовместимо с загрузкой моделей в видеопамять при холодном старте (ADR-0007, рассмотренные альтернативы).

Службы разделены на профили:

| Профиль | Состав | Назначение |
|---|---|---|
| `core` | Три экземпляра vLLM, PostgreSQL, Qdrant | Без них система не работает |
| `app` | API с оркестратором, мок учётной системы | Включается, когда в `backend/` и `mock-erp/` появятся Dockerfile |
| `observability` | Langfuse, Prometheus, Grafana | Инструменты разработчика; отказ профиля не влияет на остальные |

Целевая схема — четыре группы узлов: приложения, хранилища, инференс в отдельной сетевой зоне, наблюдаемость. Она описана в модели C4 (`workspace.dsl`), порядок перехода — `migration-path.md`, раздел 3.

## 2. Развёртывание

Узел **прерываемый**: его могут остановить в любой момент. Отсюда требования к развёртыванию:

- **одна команда** — `infra/bootstrap.sh` выполняет всё: от системных пакетов и драйвера до проверки ответа модели;
- **идемпотентность** — повторный запуск на настроенном узле ничего не пересоздаёт и не перевыпускает секреты;
- **никаких ручных шагов** — настройка, не зафиксированная в коде, считается утраченной.

После перезагрузки юнит systemd выполняет `bootstrap.sh --boot`. Пакеты, образы и веса уже на диске, поэтому стек поднимается за минуты. Первым поднимается `core`; наблюдаемость запускается следом в фоне и готовность не задерживает (ADR-0007).

Веса моделей хранятся на хосте и монтируются в контейнеры, в образах их нет: повторно скачивать 15 ГБ при каждом пересоздании контейнера недопустимо. Экземпляры vLLM стартуют строго последовательно, потому что каждый при запуске измеряет свободную видеопамять.

Места, которые невозможно проверить без узла с ускорителем, помечены в исходниках комментарием `ПРОВЕРИТЬ НА МАШИНЕ`.

## 3. Конфигурация и секреты

Конфигурация и секреты разделены по `security.md`, раздел 5:

- `infra/.env` — только несекретная конфигурация: адреса служб, порты, имена моделей, параметры поиска. Файл создаётся из `infra/.env.example` и в git не попадает.
- Секреты — отдельные файлы в `infra/secrets/`, в контейнеры они передаются механизмом Docker secrets. `bootstrap.sh` генерирует их один раз и при повторном запуске не перевыпускает: иначе они рассогласуются с уже созданными томами хранилищ.

Образы, умеющие читать секрет из файла, получают путь к нему. Остальным секрет передаёт обёртка точки входа: при старте контейнера она переводит его в переменную окружения процесса. В описание контейнера и в аргументы командной строки секрет не попадает. Перечень секретов и способ передачи для каждой службы — `infra/README.md`. Порядок действий при компрометации — `security.md`, раздел 5.

## 4. Сеть

Все порты служб публикуются только на локальном интерфейсе узла. Доступ с рабочей машины — через SSH-туннель.

Ограничение исходящего трафика по ADR-0001 двухуровневое. Действительная граница — правила группы безопасности на стороне площадки. Вспомогательный уровень — локальная блокировка известных адресов внешних сервисов генеративных моделей в `bootstrap.sh`: она защищает от случайного обращения и границей безопасности не является (`security.md`, раздел 6).

## 5. Устойчивость

Поведение при отказе зависимостей задано ADR-0007 и реализуется в приложении: бюджеты времени, ограничение повторов, размыкатель на трёх зависимостях.

На уровне инфраструктуры:

- службы перезапускаются автоматически (`restart: unless-stopped`), демон Docker настроен с `live-restore`;
- проверки состояния заданы для экземпляров vLLM, PostgreSQL и хранилищ Langfuse. Готовность Qdrant проверяется с хоста, потому что в его образе нет средств для проверки изнутри;
- объём журналов контейнеров ограничен ротацией, чтобы они не отнимали диск у весов и томов.

## 6. Резервное копирование и восстановление

Цели и порядок восстановления узла заданы ADR-0007, состав резервируемых данных — `security.md`, раздел 7. Сохранность критична только для хранилища состояния: в нём аудиторский след, который невозможно восстановить иначе. Векторные представления, веса моделей и данные мока воспроизводятся из репозитория и исходных данных.

**Текущее состояние.** Ежедневная выгрузка хранилища состояния на отдельный том в `bootstrap.sh` пока не реализована; она появится вместе с первым реальным запуском. Тома Docker переживают перезапуск контейнеров, но не пересоздание узла.

## 7. Наблюдаемость

- **Аудиторский след** ведётся в PostgreSQL профиля `core` по модели данных и от наблюдаемости не зависит.
- **Трассировка вызовов модели** — Langfuse, инструмент разработчика; источником доказательств он не является.
- **Метрики** собирает Prometheus — с экземпляров vLLM, Qdrant и API; Grafana их отображает.

Распределённая трассировка через отдельный сборщик отнесена к целевому состоянию: при одном узле и одном процессе приложения выигрыш не оправдывает дополнительной службы (`technology-decisions.md`, раздел 7).

## 8. Сборка и выпуск

Теги образов сторонних служб заданы явно в `docker-compose.yml` и `infra/.env`; для Langfuse, PostgreSQL и Redis — с точностью до основной версии. Образы API и мока учётной системы собираются на узле из `backend/` и `mock-erp/` при запуске профиля `app`.

Изменение кода выпускается коммитом в репозиторий и повторным запуском `bootstrap.sh` на узле. Изменения моделей, формулировок запросов, правил, корпуса и параметров поиска выпускаются в порядке, описанном в MLOps-записке (`mlops.md`, раздел 3).

Автоматическая сборка с порогами качества и постепенное выкатывание версий отнесены к целевому состоянию: первой нужен эталонный набор случаев, второму — продуктивный поток обращений (`technology-decisions.md`, раздел 5).
