# ADR-0002. Разделение ответственности между агентами и детерминированными инструментами

| | |
|---|---|
| Статус | Accepted (принято) |
| Дата | 03.09.2026 |
| Контекст решения | Определение состава агентов и границы применения языковой модели |
| Связанные решения | ADR-0001 (локальный контур), ADR-0004 (классификация правил) |

## Контекст

Предметная область содержит 46 правил выбора способа устранения, 20 правил определения гарантийности и 10 правил согласования, полученных из действующей сервисной практики. При разметке этих правил выяснилось, что примерно две трети вычисляются однозначно по проверяемым признакам (сравнение дат, соответствие кода ошибки справочнику, сравнение суммы с порогом, наличие авторизации центра по бренду), а оставшаяся треть требует интерпретации свободного описания, данного человеком.

Требуется определить, какая часть логики реализуется языковой моделью, а какая — обычным кодом. Решение принимается до начала разработки, поскольку определяет состав компонентов, объём тестирования и характер отказов системы.

## Критерии выбора

| № | Критерий | Обоснование |
|---|---|---|
| C-1 | Воспроизводимость результата | Одинаковый вход должен давать одинаковый выход там, где это возможно |
| C-2 | Проверяемость на защите и при эксплуатации | Результат должен поддаваться объяснению через правило, а не через вероятность |
| C-3 | Стоимость отладки и тестирования | Каждый агент требует промптов, трассировки, обработки отказов и набора тестов |
| C-4 | Расход ресурсов инференса | Ограничен объёмом видеопамяти по ADR-0001 |
| C-5 | Устойчивость к ошибкам модели | Ошибка в детерминированной части исключена по построению |

## Рассмотренные варианты

### Вариант A. Агентная реализация всей логики

Каждый шаг процесса выполняется отдельным агентом, включая проверку сроков гарантии, сравнение суммы с порогом согласования и подбор исполнителя.

Отклонён. Нарушает C-1 и C-5: результат сравнения двух дат становится вероятностным без каких-либо преимуществ. Нарушает C-2: объяснение «модель так решила» неприемлемо для решения о гарантийности. Нарушает C-3 и C-4: каждый дополнительный агент увеличивает объём отладки и число вызовов инференса. Кроме того, вариант противоречит исходному тезису о том, что платформа не подменяет детерминированную логику учётной системы.

### Вариант B. Единственный агент с набором инструментов

Одна языковая модель в цикле рассуждения с доступом ко всем инструментам.

Отклонён. При объёме контекста, включающем справочники, документацию, историю обслуживания и правила, качество рассуждения модели среднего размера падает. Отсутствует возможность раздельной проверки этапов: невозможно определить, ошибка произошла при идентификации оборудования или при подборе документации. Затрудняется реализация прерывания на подтверждение человеком, поскольку состояние не структурировано по этапам.

### Вариант C. Разделение по природе задачи

Агентом становится только тот шаг, который требует интерпретации неструктурированного содержания. Всё, что вычисляется по проверяемым признакам, реализуется обычным кодом.

Принят.

## Решение

Применяется правило отнесения: **компонент реализуется как агент, если его вход содержит текст или изображение, порождённые человеком, а выход требует интерпретации, не сводимой к сопоставлению со справочником. Во всех остальных случаях компонент реализуется как детерминированный инструмент.**

Состав по этому правилу:

| Компонент | Тип | Основание |
|---|---|---|
| Оркестратор | Стейт-машина | Управление состоянием, ветвление, прерывание, деградация. Рассуждения не требует |
| Context Agent | Агент | Извлечение идентификаторов оборудования и партнёра из свободного текста обращения |
| Knowledge Agent | Агент | Сопоставление описанного человеком симптома с документацией и решёнными случаями |
| Policy Agent | Агент | Оценка применимости одного правила requires_evaluation к подтверждённым фактам; способ выполнения задан каталогом и применяется кодом |
| Распознавание изображения | Инструмент с моделью | Извлечение идентификационных данных; результат обязательно сверяется со справочником |
| Проверка срока гарантии и статуса договора | Инструмент | Сравнение дат и статусов |
| Определение типа исполнения и выбор центра | Инструмент | Проверка территории, компетенции, авторизации по бренду, доступности |
| Подбор исполнителя | Инструмент | Цепочка приоритетов и фильтрация по атрибутам |
| Определение уровня согласования | Инструмент | Сравнение суммы с порогом и с ценой изделия |
| Исполнитель действий | Детерминированный код | Исполнение не должно зависеть от вероятностной модели |

Итого три агента и детерминированное окружение. Ограничение числа агентов является осознанным: каждый дополнительный агент увеличивает объём отладки и число точек отказа, не добавляя способности, которой не даёт инструмент.

**Дополнительное ограничение.** Языковая модель не имеет прямого доступа к учётной системе. Любое изменение выполняется исполнителем после подтверждения человеком. Фактические сведения модель не порождает, а получает вызовом инструмента.

### Реализация оркестратора: явный конечный автомат

Оркестратор реализуется как явный конечный автомат на состояниях, хранимых в собственной схеме, без применения специализированной библиотеки оркестрации агентов.

**Рассмотренная альтернатива — библиотека оркестрации с графом состояний.** Она предоставляет ветвление, сохранение контрольных точек и приостановку с возобновлением, то есть ровно то, что требуется по ADR-0008.

**Основание отказа.** Собственная схема уже содержит состояние процесса: шаг, снимок состояния, вызовы инструментов, версия набора артефактов. Эти записи являются частью аудиторского следа и служат доказательной базой для критериев приёмки. Библиотека привнесла бы **второй механизм персистентности** со своим форматом контрольных точек, то есть два источника истины о состоянии обращения и задачу их согласования.

Это тот же довод, по которому отклонено дублирование мастер-данных (ADR-0006) и графовое хранилище (ADR-0003): вторая копия данных создаёт задачу синхронизации, не давая выигрыша.

**Дополнительные основания.** Набор состояний конечен и известен заранее; точка приостановки одна; переходы должны быть прослеживаемы в записи аудита, а не в формате стороннего инструмента; зависимость от библиотеки с активно меняющимся интерфейсом добавляет риск при сроке в три недели.

**Условие пересмотра.** Появление нескольких точек приостановки, динамически определяемых маршрутов либо параллельных ветвей с объединением результатов, где собственная реализация станет дороже сопровождения библиотеки.

## Последствия

**Положительные.** Две трети логики воспроизводимы и покрываются обычными тестами. Ошибка модели не может привести к неверному определению порога согласования или к выбору центра без нужной авторизации. Объём промптов и тестов промптов ограничен тремя компонентами. Каждое решение объяснимо: либо ссылкой на правило, либо ссылкой на источник в документации.

**Отрицательные и принимаемые.** Правила должны быть заранее размечены на два класса, и эта разметка становится сопровождаемым артефактом (см. ADR-0004). При изменении правила требуется решение, к какому классу оно относится. Часть гибкости теряется: система не сможет обработать ситуацию, не предусмотренную ни правилом, ни документацией, и в таком случае обязана эскалировать её человеку, а не строить предположение.

## Compliance & Ethics

Раздел обязателен для решений, затрагивающих применение языковых моделей.

**Риск фактологических ошибок.** Настоящее решение является основной мерой снижения этого риска: две трети логики выведены из зоны действия вероятностной модели и не могут дать неверный результат по построению. Ошибка модели не способна привести к неверному определению срока гарантии, порога согласования или к выбору сервисного центра без требуемой авторизации по бренду. Остаточный риск локализован в трёх агентах и компенсируется обязательными ссылками на источники и проверкой упомянутых сущностей на существование.

**Объяснимость.** Решение сознательно жертвует частью гибкости в пользу объяснимости: каждый результат прослеживается либо до конкретного правила, либо до фрагмента документации. Для процесса, где определяется платность ремонта и расходуются средства партнёра, объяснимость приоритетнее полноты охвата ситуаций.

**Предвзятость.** Детерминированная часть логики предвзятости не подвержена. В агентной части риск ограничен интерпретацией описания неисправности и не затрагивает решений о деньгах и обязательствах, поскольку они вычисляются инструментами.

**Устойчивость к манипуляции.** Инъекция в тексте обращения способна повлиять на поведение агента, но не на инструмент: пороги, авторизации и права проверяются кодом, а не моделью. Языковая модель не имеет прямого доступа к учётной системе, поэтому успешная манипуляция не может привести к изменению данных без подтверждения оператором.

**Границы применимости.** Система не обрабатывает ситуации, не предусмотренные ни правилом, ни документацией. В таких случаях обращение эскалируется человеку. Это ограничение принято осознанно и подлежит проговариванию при защите решения.

## Проверка соблюдения

- В коде отсутствуют вызовы языковой модели для вычислений, сводимых к сравнению значений.
- Каждый вызов инструмента фиксируется в трассировке с указанием инициировавшего его агента.
- Критерии приёмки AC-2, AC-7, AC-10.
