# ADR-0006. Адаптер учётной системы

| | |
|---|---|
| Статус | Accepted (принято) |
| Дата | 08.09.2026 |
| Контекст решения | Способ взаимодействия платформы с учётной системой |
| Связанные решения | ADR-0002 (разделение ответственности), ADR-0003 (стратегия поиска) |

## Контекст

Платформа получает все фактические сведения из учётной системы: оборудование, партнёры, договоры, цены, остатки запчастей, сервисные центры, исполнители, история обслуживания. Она же создаёт в ней черновики документов.

Три обстоятельства определяют решение.

**Продуктивная система недоступна.** Разработка ведётся вне корпоративного контура, подключение к реальному ландшафту в рамках MVP невозможно.

**Учётная система не единственно возможная.** Референсной выбрана SAP S/4HANA Service, но платформа по постановке задачи не должна быть привязана к конкретному вендору.

**Права проверяются в источнике.** Данные вне зоны ответственности пользователя не должны попадать в контекст модели (PRD, раздел 3.3). Значит фильтрация выполняется на уровне доступа к данным, а не после получения ответа.

## Критерии выбора

| № | Критерий | Обоснование |
|---|---|---|
| C-1 | Независимость доменной логики от вендора | Требование к платформе |
| C-2 | Возможность разработки без продуктивной системы | Ограничение MVP |
| C-3 | Применение контекста авторизации ко всем обращениям | Требование безопасности |
| C-4 | Безопасность повторного выполнения записи | Возможны повторы и таймауты |
| C-5 | Отсутствие лишних обращений в пределах одного разбора | Несколько агентов запрашивают одни и те же сведения |

## Рассмотренные варианты

### Вариант A. Прямые вызовы учётной системы из кода агентов

Отклонён. Доменная логика оказывается связанной с форматом конкретного вендора, разработка без продуктивной системы невозможна, контекст авторизации приходится передавать в каждом месте вызова, что делает пропуск вопросом времени.

### Вариант B. Слой доступа к данным с моделью учётной системы

Абстракция создаётся, но оперирует понятиями вендора.

Отклонён. Агенты остаются связанными с чужой моделью, а при смене учётной системы меняются и они. Нарушает C-1.

### Вариант C. Порт с собственной доменной моделью и сменными реализациями

Принят.

## Решение

Применяется схема портов и адаптеров.

**Порт** описан в терминах собственной доменной модели: оборудование, партнёр, договор, сервисный центр, исполнитель, запчасть, черновик документа. Ни одно понятие вендора за пределы адаптера не выходит. Агенты и инструменты знают только порт.

**Рабочая реализация MVP:** `Application → ErpPort → SapODataAdapter → HTTP OData façade → PostgreSQL`.

`backend/adapters/sap_odata.py` реализует существующий порт, а `backend/api/main.py` создаёт именно этот адаптер. Отдельный mock ERP сохраняет связанные синтетические equipment, models, partners, contracts, history, centers, technicians, parts, цены и work order drafts. Статические ответы вместо базы не используются. Старые `/v1` endpoints и MockErpAdapter остаются для совместимости и регрессии; live application их не вызывает.

**Custom SAP-like контракт:** сервис `ZAI_SERVICE` по адресу `/sap/opu/odata4/sap/zai_service/0001/`. Это OData V4-like subset, который концептуально мог бы быть опубликован custom RAP/OData service в S/4HANA. Полная реализация OData и совместимость с конкретным released SAP standard API не заявляются.

Поддержаны service document, `$metadata`, девять Entity Sets, key lookup, закрытый набор `$filter`, `$select`, `$expand=Model,BusinessPartner` у Equipment, JSON `value`, ISO даты, структурированные ошибки и HTTP 400/401/403/404/409/500. Полный поддерживаемый контракт — в `mock-erp/README.md`; произвольные запросы, пагинация и `$batch` не поддержаны.

Запись получает `X-CSRF-Token: Fetch` у корня сервиса; POST требует этот токен под тем же контекстом и `Idempotency-Key`, совпадающий с телом. Токен действует 30 минут, подписан служебным секретом и привязан к пользователю, роли, партнёру и эффективным территориям. SAP session/cookie infrastructure не имитируется.

`ERP_BASE_URL` задаёт endpoint, существующий `MOCK_ERP_TOKEN_FILE` — файл служебного токена. Адаптер передаёт обязательный AuthContext; façade повторно проверяет пользователя и права в источнике, затем использует прежние операции PostgreSQL с ACL, аудитом и идемпотентностью. Бюджеты: чтение 5 секунд, запись 15 секунд; один повтор транспорта/5xx допустим для чтения и записи с ключом, без ключа запись не повторяется (ADR-0007).

**Будущее подключение:** продуктивный SAP S/4HANA недоступен и вне scope MVP. Сохраняется ErpPort; при подключении меняются endpoint, auth/config и при необходимости mapping конкретного SAP API в адаптере. Совместимость с реальным landscape не проверена; одного изменения URL может быть недостаточно.

**Контекст авторизации — обязательный параметр каждого метода порта.** Не поле объекта, не глобальная переменная, не заголовок, добавляемый где-то в середине. Вызов без него невозможен по сигнатуре. Адаптер передаёт контекст, а источник применяет ограничения по территориям пользователя до возврата данных и возвращает отказ, а не пустой результат, при обращении к объекту вне зоны ответственности.

Различие существенно: пустой результат неотличим от отсутствия данных и скрывает ошибку разграничения, тогда как явный отказ фиксируется в аудите и виден при разборе.

**Идемпотентность записи.** Создание черновика документа принимает ключ идемпотентности, формируемый из идентификатора решения. Повторный вызов с тем же ключом возвращает ранее созданный документ и не создаёт второй. Повторы при таймаутах допустимы только для операций чтения и для записи, защищённой ключом.

**Кэш в пределах одного обращения.** Ответы на чтение сохраняются на время разбора одного обращения и переиспользуются при повторном запросе тех же сведений разными агентами. Область действия ограничена одним обращением, время жизни — временем разбора, ключ включает контекст авторизации.

Ограничение области действия принципиально. Кэш, переживающий обращение, привёл бы к выдаче устаревших сведений об остатках и статусе договора и к возможности отдать данные, полученные под правами другого пользователя.

**Кэширование итоговых рекомендаций не применяется.** Обоснование: результат зависит от прав запрашивающего, поэтому один и тот же ответ для разных ролей недопустим; кроме того, он опирается на изменяемые сведения (остаток запчасти, статус договора, доступность исполнителя), из-за чего вчерашняя рекомендация может оказаться неверной сегодня. При этом доля точных повторов обращений близка к нулю: обращения формулируются свободно и привязаны к конкретному оборудованию.

## Последствия

**Положительные.** Доменная логика не зависит от вендора; смена учётной системы затрагивает один компонент. Разработка ведётся без продуктивной системы, а результат воспроизводим у проверяющего. Пропустить контекст авторизации невозможно по сигнатуре метода. Повторное подтверждение не создаёт второй документ. Число обращений в пределах разбора сокращается без риска устаревания.

**Отрицательные и принимаемые.** Появляется слой преобразования, который нужно сопровождать. SapODataAdapter реализован и проверен по HTTP против SAP-like мока с PostgreSQL, включая путь приложения. Интеграция с реальным SAP S/4HANA не проверена; mapping может отличаться. Собственная доменная модель может не покрыть особенности конкретного вендора, что потребует её расширения.

## Compliance & Ethics

**Разграничение доступа.** Адаптер — единственная точка получения фактов, поэтому он обязательно передаёт контекст прав; источник проверяет его перед возвратом фактов. Централизация здесь снижает риск: ошибка возможна в одном компоненте, а не в каждом месте вызова. Проверяется критериями AC-3 и AC-4.

**Отказ вместо пустого результата.** Обращение к объекту вне зоны ответственности возвращает отказ и фиксируется в аудите. Молчаливое сокрытие данных недопустимо: оно неотличимо от их отсутствия и мешает разбору инцидентов.

**Достоверность данных.** Ограничение кэша временем разбора одного обращения гарантирует, что решение принимается на актуальных сведениях. Снимок фактов сохраняется для аудита и идемпотентного повторения той же записи. Для нового разбора источником мастер-данных остаётся ERP.

**Границы ответственности при подключении к продуктивной системе.** Адаптер OData не проверен на реальном ландшафте. До проверки любые утверждения о совместимости являются проектными предположениями и должны обозначаться как таковые.

## Проверка соблюдения

- Ни один метод порта не может быть вызван без контекста авторизации.
- Запрос объекта чужой территории возвращает отказ, событие попадает в аудит.
- Повторное создание документа с тем же ключом возвращает существующий.
- В коде агентов и инструментов отсутствуют понятия конкретного вендора.
- Критерии приёмки AC-3, AC-4, AC-5.

Проверки реализации: `tests/unit/test_sap_odata_adapter.py` (контекст, преобразование ошибок, бюджеты повторов, CSRF); `tests/integration/test_sap_odata.py` (настоящий HTTP → PostgreSQL, ACL, ключи, конфликт и конкурентный replay); интеграционные тесты оркестратора и `tests/e2e/test_slice_api.py` используют SapODataAdapter.
