# ADR-0003. Стратегия поиска по технической документации

| | |
|---|---|
| Статус | Accepted (принято) |
| Дата | 05.09.2026 |
| Уточнение | 22.09.2026: добавлена альтернатива PostgreSQL + pgvector; принятое решение и runtime не изменены |
| Контекст решения | Выбор способа извлечения релевантных фрагментов документации для Knowledge Agent |
| Связанные решения | ADR-0001 (локальный контур), ADR-0002 (разделение ответственности) |

## Контекст

Knowledge Agent получает описание неисправности и должен найти релевантные фрагменты в корпусе, состоящем из руководств производителей, внутренних технических бюллетеней и записей о ранее решённых обращениях.

Ключевая особенность предметной области: **запросы имеют двойственную природу**.

| Тип запроса | Пример | Что требуется от поиска |
|---|---|---|
| Точный идентификатор | Код ошибки 50.2, C6000, E000020; артикул запчасти; обозначение модели | Точное совпадение редкого токена |
| Свободное описание | «Не печатает, полосы на листе, шумит при подаче» | Семантическая близость к иначе сформулированному тексту |

Оба типа встречаются как по отдельности, так и в одном обращении. В справочнике кодов ошибок около 137 записей, и код часто является единственным надёжным ключом к нужному разделу руководства.

Дополнительное ограничение: результат поиска обязан учитывать права пользователя, поскольку часть корпуса имеет уровень доступа «внутренний» (см. PRD, раздел 3.3).

## Критерии выбора

| № | Критерий | Обоснование |
|---|---|---|
| C-1 | Нахождение точных идентификаторов | Код ошибки — основной ключ к диагнозу |
| C-2 | Устойчивость к переформулированию | Обращение написано человеком, не техническим языком |
| C-3 | Возможность фильтрации по правам в самом запросе | Требование PRD: фильтрация в источнике, а не постфактум |
| C-4 | Трудозатраты на реализацию и сопровождение | Ограниченный срок до 25.09 |
| C-5 | Расход видеопамяти | Конкуренция с языковой моделью и моделью зрения по ADR-0001 |

## Рассмотренные варианты

### Вариант A. Только плотный (векторный) поиск

Единый индекс векторных представлений фрагментов, поиск по косинусной близости.

Хорошо: устойчив к переформулированию, покрывает C-2; одна подсистема, минимальные трудозатраты.

Плохо: систематически теряет точные идентификаторы. Код вида «50.2» при токенизации распадается, а его векторное представление оказывается близким к другим числовым обозначениям, семантически не связанным. Для корпуса, где код ошибки является главным ключом, это отказ по C-1. Кроме того, преподавательскими требованиями простой векторный поиск прямо назван недостаточным.

### Вариант B. Только разреженный поиск (BM25)

Полнотекстовый поиск по совпадению термов с весами.

Хорошо: точные идентификаторы находит безупречно, полностью покрывает C-1; дёшев по ресурсам, не требует видеопамяти.

Плохо: не находит документ, если в обращении употреблены иные слова, чем в руководстве. Формулировка «не печатает» не совпадёт с «отсутствует изображение на носителе», а именно так пишут в технической документации. Отказ по C-2.

### Вариант C. Гибридный поиск с объединением результатов

Два индекса по одному и тому же набору фрагментов: плотный и разреженный. Запрос выполняется в оба, результаты объединяются ранговым слиянием (Reciprocal Rank Fusion).

Хорошо: закрывает C-1 и C-2 одновременно, что для двойственной природы запросов является не удобством, а необходимостью. Оба индекса размещаются в одном хранилище с общей схемой метаданных, поэтому фильтрация по правам применяется единым условием к обоим (C-3). Ранговое слияние не требует обучения и настраивается одним параметром. Разреженная часть видеопамяти не потребляет (C-5).

Плохо: два индекса вместо одного, необходимость перестраивать оба при изменении корпуса; появляется параметр слияния, который нужно подбирать; для оценки качества требуется набор тестовых запросов.

### Вариант D. Поиск по графу знаний (GraphRAG)

Построение графа сущностей (оборудование, модель, отказ, код ошибки, документ, решённый случай) с обходом связей при поиске.

Отклонён для MVP по трём причинам.

Первая, содержательная: связи, ради которых обычно строится граф, в данной архитектуре уже доступны иным способом. Цепочка «оборудование → модель → история обслуживания → применённая запчасть» является отношением в учётной системе и извлекается вызовом адаптера (ADR-0002). Граф дублировал бы эти данные, создавая вторую точку истины и задачу синхронизации.

Вторая, ресурсная: отдельное хранилище, схема, загрузка, поддержание согласованности — порядка пятнадцати часов при остром дефиците срока (C-4).

Третья, безопасность: генерация языковой моделью запросов на языке графа расширяет площадь атаки за счёт возможности внедрения инструкций в запрос. Смягчение требует шаблонизации и параметризации запросов, что добавляет работы сверх названной оценки.

Решение не является окончательным отказом: см. раздел «Условие пересмотра».

### Вариант E. PostgreSQL + pgvector и лексическая ветвь

Векторный поиск через pgvector вместе с PostgreSQL full-text search либо BM25-подобной лексической ветвью. Штатные `ts_rank`/`ts_rank_cd` PostgreSQL не тождественны BM25; для именно BM25 потребовалась бы отдельная реализация или расширение. Гибридное объединение с full-text search и RRF прямо описано в [документации pgvector](https://github.com/pgvector/pgvector#hybrid-search); фильтрация метаданных может задаваться SQL-условиями.

При текущем корпусе — 9 документов, 46 фрагментов — PostgreSQL/pgvector по производительности был бы достаточен: это архитектурная оценка масштаба, а не результат сравнительного benchmark. PostgreSQL уже присутствует в системе; главное преимущество варианта — меньше инфраструктурных компонентов и единые средства эксплуатации.

Qdrant выбран не из-за отсутствия этих возможностей у pgvector. Поиск отделён от транзакционного состояния процесса; в Qdrant dense и sparse представления, одинаковый metadata filter обеих ветвей и rank fusion доступны через единый retrieval-oriented механизм. Не требуется собирать и сопровождать такой поисковый конвейер вокруг базы состояния. Корпус, индексы и мощность retrieval можно развивать независимо от transactional DB. Цена решения — отдельный сервис и его эксплуатация. При приоритете минимального числа компонентов PostgreSQL/pgvector остаётся разумной альтернативой.

## Решение

Применяется **вариант C**: гибридный поиск, объединяющий плотное векторное представление и разреженное представление BM25 по единому набору фрагментов, с ранговым слиянием результатов.

Параметры реализации:

- Оба представления хранятся в одном векторном хранилище в рамках одной коллекции, что обеспечивает единую фильтрацию по метаданным.
- Метаданные фрагмента включают уровень конфиденциальности документа, класс оборудования и модель. Фильтр по правам передаётся в запрос и применяется до ранжирования.
- Разбиение на фрагменты выполняется по разделам документа; строки таблиц кодов ошибок сохраняются целиком и не разрываются между фрагментами.
- Модель векторных представлений размещается локально в соответствии с ADR-0001.
- Переранжирование результатов вторичной моделью в MVP не применяется: выигрыш в качестве не оправдывает дополнительного расхода видеопамяти и задержки. Отнесено к целевой архитектуре.

## Последствия

**Положительные.** Оба типа запросов обрабатываются одним механизмом. Фильтрация по правам выполняется в источнике и не может быть обойдена через одну из ветвей поиска. Отсутствие графа снижает число компонентов и площадь атаки. Разреженная часть не конкурирует за видеопамять.

**Отрицательные и принимаемые.** Поддерживаются два индекса, требуется их согласованная перестройка при изменении корпуса. Появляется параметр слияния, подбираемый эмпирически; для этого необходим набор из нескольких десятков тестовых запросов с известными правильными ответами, который становится сопровождаемым артефактом. Многошаговые вопросы, требующие последовательного обхода связей между сущностями, обрабатываются хуже, чем при графовом поиске; в MVP такие вопросы покрываются вызовами адаптера, а при невозможности ответа обращение эскалируется.

## Compliance & Ethics

**Риск фактологических ошибок.** Поиск является основным средством заземления ответа на источник. Ответ без найденных фрагментов не формируется: при пустой выдаче обращение эскалируется человеку, а не дополняется внутренним знанием модели. Каждое утверждение в рекомендации сопровождается ссылкой на конкретный фрагмент.

**Разграничение доступа.** Фильтр по уровню конфиденциальности применяется к обоим представлениям одновременно. Раздельная фильтрация недопустима: она создала бы возможность получить закрытый фрагмент через одну ветвь поиска в обход другой. Проверяется критерием приёмки AC-4.

**Устойчивость к манипуляции.** Текст обращения является недоверенным входом и используется для формирования поискового запроса. Запрос не транслируется в исполняемый язык запросов к хранилищу, что исключает соответствующий класс внедрений. Это одно из оснований отказа от графового поиска в MVP.

**Полнота и границы.** Корпус ограничен двумя классами оборудования. По остальным классам поиск заведомо неполон, что должно отражаться в ответе как отсутствие данных, а не как отсутствие проблемы.

## Условие пересмотра

Включение графового поиска рассматривается 20.09.2026 при выполнении двух условий: основной сценарий работает сквозным образом, и остаётся резерв времени. При включении объём ограничивается четырьмя типами узлов, а запросы к графу строятся исключительно по параметризованным шаблонам без генерации языка запросов моделью.

При отрицательном решении графовый поиск остаётся в целевой архитектуре с указанием причины отказа.

## Проверка соблюдения

- Запрос к хранилищу содержит фильтр по правам во всех случаях без исключения.
- Тестовый набор содержит запросы обоих типов: по точному коду ошибки и по свободному описанию.
- Критерии приёмки AC-2, AC-4.
