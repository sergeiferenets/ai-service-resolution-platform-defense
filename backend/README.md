# Backend

Платформа: API, оркестратор, механизм правил, детерминированные инструменты, адаптер
учётной системы и три настоящих агента: Context, Knowledge и Policy. Policy оценивает только применимость rules requires_evaluation; заглушки остаются тестовыми.

## Структура

- `domain/` — нейтральная доменная модель и контекст авторизации (ADR-0006).
- `adapters/` — ErpPort, SapODataAdapter по HTTP к custom OData façade мока, кэш чтения на одно обращение. MockErpAdapter сохранён для регрессии старого /v1, в live application не используется.
- `llm/` — общий слой вызова моделей без знания предметной области: клиент к vLLM с
  бюджетом ADR-0007, структурированный вывод со схемой, проверкой, одним повтором и отказом,
  версия формулировки запроса.
- `guardrails/input/` — входной контроль текста обращения (security 3.1): внедрение
  инструкций, вне области, персональные данные.
- `rules/` — машиночитаемый свод правил, механизм применения (ADR-0004), срочность.
- `tools/` — инструменты ADR-0002: гарантия, тип исполнения и кандидаты, согласование,
  справочник кодов ошибок.
- `agents/context/` — Context Agent: извлечение из текста, чтение таблички, определение
  оборудования (текст → фото → партнёр и модель, PRD 5.3), проверка кода, признак риска.
- `agents/stubs.py` — заглушки; `agents/factory.py` — сборка агентов для работы с моделями.
- `orchestrator/` — конечный автомат (`machine.py`, `states.py`), хранилище состояния,
  запись вызовов в TOOL_CALL, исполнитель черновика, схема и загрузчик платформы.
- `api/` — HTTP API.

## Запуск

Образ собирается из корня репозитория (`backend/Dockerfile`); в compose — сервис `api`
профиля `app`, запускается вместе с `core`. При старте контейнера: миграции схемы,
загрузка справочников платформы (территории, пользователи, доступ, правила), сервер.
Мастер-данных учётной системы в образе и в базе платформы нет. Для Context Agent нужен
работающий vLLM: без ключа `VLLM_API_KEY_FILE` сервис не стартует, при недоступности
модели обращение передаётся человеку.

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/requests` | Принять обращение и выполнить разбор до рекомендации |
| GET | `/v1/requests/{id}` | Состояние, идентификация, признаки риска, рекомендация, решение, черновик |
| GET | `/v1/requests/{id}/steps` | Шаги процесса с вызовами и версией набора артефактов |
| POST | `/v1/requests/{id}/confirm` | Подтверждение или отклонение рекомендации диспетчером |
| POST | `/v1/requests/{id}/approve` | Согласование сервис-менеджером |

Тело `POST /v1/requests`: `text`, необязательные `impact`, `partner_id` (сотрудник регистрирует
обращение за партнёра), `image_base64` и `image_content_type` (фотография таблички, JPEG или
PNG до 5 МБ). Пользователь передаётся заголовком `X-User-Id` — временная замена единого входа;
права берутся из реестра платформы, а не из заголовка.

## Тесты

- `tests/unit` — без внешних зависимостей, модель подменяется;
- `tests/integration` — против мока и PostgreSQL, база платформы `servicedesk_test`;
- `tests/eval` — набор оценки Context Agent на живых моделях;
- `tests/e2e/test_slice_api.py` — критерии готовности через API.
