# Мультиагентная AI-платформа анализа и разрешения сервисных обращений

> **Public defense snapshot.** Публичная версия выпускного проекта для предварительной
> проверки преподавателями. История разработки и внутренние рабочие материалы находятся
> в отдельном приватном репозитории и в этот snapshot не включены. Демонстрационные данные
> в этой версии синтетические и подготовлены для безопасной публикации.

MVP на примере гарантийного и платного ремонта оборудования. Выпускная работа курса OTUS
«AI-архитектор».

Учётные системы хорошо автоматизируют детерминированную часть сервисного процесса: регистрацию
обращения, карточку оборудования, движение техники, учёт запчастей, фактурирование. Платформа
занимается тем, что остаётся за этой границей: обращение приходит в свободной форме и без
идентификаторов, описанный человеком симптом нужно сопоставить с кодом ошибки и разделом
документации, а часть корпоративных правил требует интерпретации контекста.

Система формирует **рекомендацию, а не решение**. Ни одно изменение в учётной системе не
совершается без подтверждения оператором.

Полное описание — [docs/prd.md](docs/prd.md).

## Как это работает

1. **Context Agent** извлекает из свободного текста идентификаторы оборудования и партнёра;
   при наличии фотографии идентификационной таблички подключается распознавание изображения.
2. **Knowledge Agent** выполняет гибридный поиск по документации, формирует гипотезу причины
   с обязательной ссылкой на источник.
3. **Policy Agent** вызывается только для `requires_evaluation` после механизма правил.
   Получает минимальный `PolicyCase`: идентификатор и условие правила, производитель,
   код ошибки, модель и цитата симптома. Возвращает `applicable`, `not_applicable` или
   `insufficient`; маршрут берётся из каталога правил, а не из ответа модели.
   `not_applicable`, `insufficient` и ошибка validation после retry ведут к человеку.
   Уточнение и возобновление описаны в [ADR-0008](docs/adr/0008-diagnostic-clarification.md),
   но runtime resume в MVP не реализован.
4. **Оркестратор** собирает рекомендацию, проводит её через выходной контроль и останавливается
   на подтверждении человеком.

После выбора маршрута инструменты, а не модель, выполняют предварительную квалификацию гарантии,
определяют уровень согласования и рассчитывают **операционную срочность**. Срочность считается
отдельно и на технический маршрут не влияет. Если в тексте обращения упомянуты падение, жидкость,
следы вскрытия или неоригинальные расходные материалы, диспетчер получает **признак риска
по гарантии** — вывода о негарантийности система не делает.

Агентов три — Context, Knowledge, Policy, — больше не предусмотрено. Всё, что вычислимо
детерминированно, реализовано инструментами: [ADR-0002](docs/adr/0002-agent-tool-separation.md).

## Архитектурные принципы

Заданы в [ADR](docs/adr/) и обязательны к исполнению.

- **Локальный контур.** Модели размещаются на собственном узле. Данные партнёров не покидают
  периметр — обезличивание невозможно без потери смысла, поскольку привязка обращения к партнёру
  и единице оборудования и есть предмет анализа.
  [ADR-0001](docs/adr/0001-local-llm-deployment.md)
- **Модель не знает фактов.** Любой факт об оборудовании, договоре, цене, остатке приходит только
  через адаптер учётной системы. Рабочий путь MVP:
  `Application → ErpPort → SapODataAdapter → custom SAP-like OData mock`.
  Это собственный ограниченный OData V4-like контракт, не released SAP standard API;
  совместимость с продуктивным SAP не проверена.
  [ADR-0006](docs/adr/0006-erp-adapter.md)
- **Рассуждение отдельно от исполнения.** Модель не имеет прямого доступа к учётной системе;
  запись выполняет детерминированный исполнитель после подтверждения человеком и сохранения
  execution grant, с ключом идемпотентности.
- **Права проверяются в источнике.** Контекст авторизации — обязательный параметр каждого метода
  адаптера и каждого поискового запроса. Обращение вне зоны ответственности даёт явный отказ,
  а не пустой результат. Фильтрация готового ответа не заменяет контроль в источнике.
  При чтении сохранённого результата права проверяются повторно; недоступное читателю
  обоснование скрывается целиком ([conformance](docs/architecture/conformance.md), раздел 2).
- **Правила делятся по достаточности данных.** Решаемые сразу по имеющимся данным, требующие
  недостающих фактов и требующие экспертной интерпретации исполняются разными механизмами.
  [ADR-0004](docs/adr/0004-rules-classification.md)
- **Поиск гибридный.** Плотное представление и BM25 в одной коллекции с ранговым слиянием.
  [ADR-0003](docs/adr/0003-retrieval-strategy.md)
- **Отказ зависимости предсказуем.** Каждый вызов ограничен по времени, повтор записи допустим
  только с ключом идемпотентности; при недоступности адаптера, поиска или распознавания
  изображения система переходит в заранее описанный деградированный режим.
  [ADR-0007](docs/adr/0007-deployment-resilience.md)
- **Рекомендации не кэшируются.** Они зависят от прав запрашивающего и от изменяемых фактов.
  Кэш ответов адаптера живёт только в пределах разбора одного обращения.

## Требования к машине

Развёртывание требует узла с ускорителем NVIDIA. Без GPU стек не поднимается: модели работают
локально, обращений к внешним сервисам в контуре продукта нет.

| Параметр | Значение | Обязательность |
|---|---|---|
| Ускоритель | NVIDIA, 48 ГБ видеопамяти | Три модели одновременно без выгрузки |
| Архитектура ускорителя | Ampere или новее | Жёсткое требование: квантование AWQ ([ADR-0005](docs/adr/0005-model-selection.md)) |
| CPU / RAM | 12 vCPU, 64 ГБ | Хранилища и профиль наблюдаемости |
| Диск | 200 ГБ | Веса моделей ~15 ГБ, образы ~20 ГБ, тома |
| ОС | Ubuntu 22.04 | Проверено на ней |

Фактический стенд — MVP GPU node с NVIDIA GeForce RTX 4090; runtime сообщает
49 140 МиБ видеопамяти. RTX 6000 Ada была плановой конфигурацией.
Фактический узел и измерения — в [плане мощностей](docs/economics/capacity-plan.md).

Сервер **прерываемый** — может быть остановлен в любой момент. Поэтому всё разворачивается
скриптом с нуля, а ручные настройки, не зафиксированные в коде, считаются утраченными.

## Быстрый старт

```bash
git clone https://github.com/sergeiferenets/ai-service-resolution-platform-defense.git
cd ai-service-resolution-platform-defense
sudo bash infra/bootstrap.sh
```

Скрипт выполняет всё сам: системные пакеты, драйвер NVIDIA, Docker с плагином compose,
NVIDIA Container Toolkit, проверку доступа к GPU из контейнера, создание `infra/.env`
с несекретной конфигурацией, генерацию секретов в `infra/secrets/`, загрузку весов моделей,
запуск стека, создание коллекции поиска и проверку, что языковая модель отвечает на русском.

Скрипт идемпотентен: сохраняет существующие секреты и данные; изменённые контейнеры могут
пересоздаваться. Сетевые правила площадки настраиваются отдельно, см. ниже.

Первый проход занимает 20–40 минут, из них большая часть — загрузка весов и образов.

## Пользовательские сценарии запуска

### Первое развёртывание на чистой машине

```bash
sudo bash infra/bootstrap.sh
```

Если драйвер NVIDIA отсутствовал и после его установки требуется перезагрузка, скрипт скажет
об этом и остановится. Чтобы перезагрузка выполнялась без оператора, поставьте в `infra/.env`:

```
AUTO_REBOOT=1
```

После перезагрузки развёртывание продолжится само — скрипт ставит юнит systemd.

### Восстановление после вытеснения сервера

Ничего делать не нужно. Юнит `service-desk-ai.service` выполняет `bootstrap.sh --boot` при
загрузке: пакеты, образы и веса уже на диске, стек поднимается за минуты. Первым поднимается
основной профиль, наблюдаемость стартует следом и работу не задерживает
([ADR-0007](docs/adr/0007-deployment-resilience.md)).

```bash
systemctl status service-desk-ai
journalctl -u service-desk-ai -f
```

### Повторный запуск после изменений в конфигурации

```bash
sudo bash infra/bootstrap.sh
```

Безопасно в любой момент. Существующие секреты и тома не затрагиваются.

### Диагностика

```bash
sudo bash infra/bootstrap.sh --check
```

Показывает версии драйвера, Docker и toolkit, состояние контейнеров и занятость видеопамяти,
ничего при этом не меняя.

### Локальный доступ к развёрнутому стенду

Все порты слушают `127.0.0.1`: узел арендованный и имеет публичный адрес, поэтому наружу
не выставлено ничего. Доступ — SSH-туннелем:

Интерфейсы ниже доступны только на развёрнутом MVP-узле через SSH-туннель; это эксплуатационные
адреса стенда, а не публичные demo URL.

```bash
ssh -N -L 8501:127.0.0.1:8501 -L 8000:127.0.0.1:8000 -L 8001:127.0.0.1:8001 -L 8002:127.0.0.1:8002 -L 8003:127.0.0.1:8003 -L 6333:127.0.0.1:6333 -L 3000:127.0.0.1:3000 -L 3001:127.0.0.1:3001 root@<адрес>
```

| Что | Адрес после туннеля |
|---|---|
| Streamlit UI | `http://127.0.0.1:8501` |
| API платформы | `http://127.0.0.1:8000/docs` |
| Языковая модель | `http://127.0.0.1:8001/v1` |
| Обработка изображений | `http://127.0.0.1:8002/v1` |
| Векторные представления | `http://127.0.0.1:8003/v1` |
| Qdrant | `http://127.0.0.1:6333/dashboard` |
| Langfuse | `http://127.0.0.1:3000` |
| Grafana | `http://127.0.0.1:3001` |

### Управление отдельными частями стека

Стек разделён на профили, чтобы отказ наблюдаемости не блокировал работу платформы.

```bash
docker compose --env-file infra/.env -f infra/docker-compose.yml --profile core --profile app --profile ui ps
docker compose --env-file infra/.env -f infra/docker-compose.yml --profile observability up -d
docker compose --env-file infra/.env -f infra/docker-compose.yml --profile core --profile app --profile ui up -d --build ui
```

| Профиль | Состав | Роль |
|---|---|---|
| `core` | Сервис инференса, PostgreSQL, Qdrant | Без него система не работает |
| `app` | API-оркестратор, SAP-like мок учётной системы | Рабочее приложение; запускается вместе с `core` |
| `ui` | Streamlit | Демонстрационный интерфейс; запускается вместе с `core` и `app` |
| `observability` | Langfuse, Prometheus, Grafana | Инструменты разработчика |

Профиль `observability` разворачивает инфраструктурные компоненты. Приложение не отправляет
LLM traces в Langfuse и не предоставляет endpoint `/metrics`; готовых проектных dashboards
Grafana в baseline нет. Фактический trace процесса хранится в собственном audit/state store.

Dockerfile приложения, мока и UI реализованы. `bootstrap.sh` запускает `core` и `app`;
демонстрационный UI включается отдельным профилем командой выше.
Порядок показа — в [ui/README.md](ui/README.md).

Ограничение исходящего трафика по ADR-0001 двухуровневое. Действительная граница — правила группы
безопасности на стороне площадки: их настраивают в панели Selectel, скрипт этого не делает.
Локальная блокировка известных адресов внешних сервисов в `bootstrap.sh` защищает только
от случайного обращения из библиотеки и границей безопасности не является.

Подробности развёртывания — [infra/README.md](infra/README.md).

## Модели

Все модели работают локально. Выбор и обоснование —
[ADR-0005](docs/adr/0005-model-selection.md), границы применимости —
[карточка модели](docs/architecture/model-card.md).

| Роль | Модель | Параметров | Квантование | Лицензия |
|---|---|---|---|---|
| Языковая | `Qwen/Qwen3-8B-AWQ` | 8,2 млрд | AWQ, 4 бита | Apache-2.0 |
| Обработка изображений | `Qwen/Qwen2.5-VL-7B-Instruct-AWQ` | 7 млрд | AWQ, 4 бита | Apache-2.0 |
| Векторные представления | `BAAI/bge-m3` | 568 млн | float16 | MIT |

Все три лицензии допускают применение в закрытом контуре и публикацию работы.

Доли видеопамяти: 0,40 под языковую модель с кэшем, 0,27 под обработку изображений,
0,08 под векторные представления. При трёх одновременно загруженных моделях измерено
≈34 505 МиБ занято из 49 140 МиБ. Медиана эталонного сквозного сценария — ≈1,72 с;
это одиночный reference case, не нагрузочный профиль.
Методика и границы измерений — в [плане мощностей](docs/economics/capacity-plan.md).

Веса лежат на хосте в `MODELS_DIR` (по умолчанию `/opt/models`) и монтируются в контейнеры.
В образах их нет: на прерываемой машине повторное скачивание 15 ГБ при каждом пересоздании
контейнера недопустимо.

Модели применяются без обучения и дообучения, на предобученных весах из открытых источников.
Данные обращений не используются для обучения и не покидают контур.

## Секреты

- `infra/.env` содержит только несекретную конфигурацию: адреса служб, порты, имена моделей,
  параметры поиска. Эталон — [`infra/.env.example`](infra/.env.example).
- Секреты — отдельные файлы в `infra/secrets/`. Их создаёт `bootstrap.sh` при первом запуске,
  каталог получает права `700` и в git не попадает ([`.gitignore`](.gitignore)).
- В контейнеры секреты передаются механизмом Docker secrets и доступны как `/run/secrets/<имя>`.
  Аргументами командной строки они не передаются и в образ не запекаются.
- Повторный запуск секреты **не меняет**: перевыпуск рассогласовал бы пароли с уже созданными
  томами баз данных. Порядок действий при компрометации —
  [docs/security/security.md](docs/security/security.md), раздел 5.
- В публичном snapshot используются синтетические демонстрационные данные. Исходные
  клиентские записи и продуктивные данные в репозиторий не включены.

Перечень секретов и способ передачи каждой службе — [infra/README.md](infra/README.md).

## Статус

MVP работает сквозным образом через Streamlit UI. Context, Knowledge и Policy Agents
реализованы без runtime stub; работают гибридный поиск и оценка `requires_evaluation`.
Подтверждение человеком и execution grant разрешают создание ERP-черновика через
`SapODataAdapter` против SAP-like mock. Измерения и eval выполнены; результаты —
в [плане мощностей](docs/economics/capacity-plan.md) и [карточке модели](docs/architecture/model-card.md).
Точный перечень реализованного, частичного и целевого — в
[conformance](docs/architecture/conformance.md).

Источник диаграмм C4 — [workspace.dsl](docs/architecture/workspace.dsl);
представления и правила экспорта — в [архитектурном разделе](docs/architecture/README.md).
